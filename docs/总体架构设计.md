# Kodo 总体架构设计

> 文档定位：描述 Kodo 当前代码仓库的总体结构、核心职责、主要运行链路与关键设计约束。
>
> 分析依据：根目录 `Cargo.toml`、各 crate/应用清单、`README.md`、桌面前后端入口及已公开的核心执行符号。本文描述的是当前仓库形态，不把尚未实现的能力当作现状。

## 1. 架构目标与边界

Kodo 是一个本地优先的项目级 Coding Agent 桌面工作台。它围绕“项目 → 会话 → Agent 执行轨迹 → 最终回答 → 变更文件”组织产品流程，允许用户在一个工作区内选择模型、Agent、Skill 和权限策略，并观察、审批或取消 Agent 的执行过程。

系统的主要架构目标如下：

1. **本地工作台边界**：以用户选定的代码项目为工作单元，不承担通用云端后台或多人协作服务职责。
2. **执行过程可观察**：模型规划、搜索、读文件、命令、写文件、审批和结果均能形成可回看的过程记录。
3. **安全默认**：未显式放宽时使用 `ask` 权限；命令执行、文件写入及危险操作进入审批流程。
4. **领域能力可复用**：会话持久化、Agent 工具循环和宿主编排独立于具体 GUI，可同时被桌面端与 CLI 使用。
5. **前后端清晰隔离**：React 负责交互和展示，Tauri 负责本地能力与 Rust 运行时桥接，WebView 不直接获得宿主文件系统或进程权限。

不在当前总体架构范围内的内容包括：云端账户系统、远程项目托管、多人实时协作、中心化数据库，以及独立部署的 Web 后端服务。

## 2. 总体分层

```text
┌──────────────────────────────────────────────────────────────┐
│ GUI：apps/desktop/src                                       │
│ React + Vite                                                │
│ 页面导航 / 会话 / Composer / Trace / Inspector / Settings    │
└───────────────────────────┬──────────────────────────────────┘
                            │ Tauri IPC（可序列化命令与 View DTO）
┌───────────────────────────▼──────────────────────────────────┐
│ Desktop Host：apps/desktop/src-tauri                          │
│ Tauri commands / 本地配置与凭据 / View 投影 / Run / Approval │
└───────────────┬──────────────────────┬───────────────────────┘
                │                      │
┌───────────────▼─────────────┐  ┌─────▼───────────────────────┐
│ Shell：crates/shell          │  │ Agent：crates/agent         │
│ 宿主侧的一轮执行编排与适配   │  │ 规划、工具循环、Provider、状态 │
└───────────────┬─────────────┘  └─────┬───────────────────────┘
                │                      │
┌───────────────▼──────────────────────▼───────────────────────┐
│ Core：crates/core                                            │
│ 项目 / 会话 / 设置等领域模型与 append-only 本地持久化         │
└──────────────────────────────────────────────────────────────┘

另有：
- CLI：crates/cli，复用 Core、Agent、Shell 提供命令行入口。
- Evals：evals，用于 Agent 行为和性能评估。
- Skills / Agents：仓库内的提示词、角色与执行约束资源。
```

依赖方向总体保持为“宿主层组合领域层”：`core` 和 `agent` 位于底层，`shell`、CLI 和 Tauri Host 在其上组装；GUI 不依赖 Rust 内部实现细节。

## 3. 工程组成

### 3.1 Cargo Workspace

根 `Cargo.toml` 使用 Rust 2021 edition 和 resolver 2，包含以下成员：

| 模块 | Crate/包名 | 主要职责 |
|---|---|---|
| `crates/core` | `kodo-core` | 项目、会话、设置等领域数据及本地日志持久化 |
| `crates/agent` | `kodo-agent` | 任务识别、规划、工具协议、模型 Provider、执行状态与副作用 |
| `crates/shell` | `kodo-shell` | 将一轮 Agent 执行组织为 CLI 和桌面宿主可复用的流程 |
| `crates/cli` | `kodo-cli` | `kodo` 命令行入口，复用前三层能力 |
| `apps/desktop/src-tauri` | `kodo-desktop` | Tauri 桌面宿主、本地命令、运行管理、审批和 View DTO |
| `evals` | eval 工具包 | Agent 基准、在线评估及评估入口 |

`kodo-agent` 仅依赖通用序列化、HTTP、Excel 解析及 Unix 系统能力，不直接依赖 `kodo-core`；持久化模型由宿主负责组合。这一安排降低了 Agent 引擎与具体存储实现的耦合。

### 3.2 Desktop 前端

`apps/desktop` 使用 React 19、Vite 8 和 Tauri 2 工具链，主要代码区域为：

| 路径 | 职责 |
|---|---|
| `src/App.tsx` | 应用壳、路由式页面切换、全局选择状态和主要数据编排 |
| `src/api.ts` | GUI 到后端能力的统一访问层，并提供演示数据适配 |
| `src/pages/` | Conversation、Trace、Archive、Settings、MCP、Agent/Skill 等领域页面 |
| `src/conversation/` | Composer、消息、回答、执行轨迹、文件/差异查看器、Markdown 渲染 |
| `src/data/` | 类型定义、live context、fixture 和演示数据 |
| `tests/visual/` | Playwright 行为与视觉回归测试 |

前端状态以 React 组件状态和上下文编排为主，没有引入独立服务端状态层。演示 UI 与真实 Tauri 模式共享主要组件，以 fixture 支撑确定性视觉验证；真实数据则经 `api.ts` 进入桌面后端。

### 3.3 Tauri Host

`apps/desktop/src-tauri` 是 GUI 与本地 Rust 能力之间的边界，主要拆分为：

| 文件 | 职责 |
|---|---|
| `src/main.rs` | Tauri 初始化、命令注册、设置/凭据/项目/Agent/Skill/MCP 等本地能力入口 |
| `src/run.rs` | 活跃运行注册、启动、取消、审批票据、审批等待与会话级放行记忆 |
| `src/view.rs` | 将内部领域对象转换为前端稳定消费的 View DTO |

该层不直接承担 Agent 推理或工具算法，而是负责桌面环境特有的生命周期、IPC、本地安全和展示适配。

## 4. 核心领域模型

### 4.1 Project 与 Workspace

项目是 Kodo 的顶层业务边界，代表用户授权 Agent 操作的代码目录。桌面 Host 为 GUI 提供项目列表和项目详情，并把项目路径传递给会话执行。项目路径不是普通聊天上下文，而是命令、搜索和写文件操作的基础工作区。

### 4.2 Session、Turn 与 Item

会话属于某个项目，并按轮次组织用户输入、Agent 输出和执行过程：

- **Session**：项目内可持续存在的对话与执行容器。
- **Turn**：一次用户提交及其对应的完整 Agent 执行。
- **Item**：一轮中的结构化过程或结果条目，例如规划、思考、搜索、读文件、命令、写文件、模型调用、审批和最终回答。

这种模型避免仅以聊天文本保存执行历史。前端既能重放用户可见的回答，也能按类型展示工具轨迹、诊断信息、变更文件和运行结果。

### 4.3 执行结果与交付结果

Agent 的执行成功不等同于文档或文件已经可靠交付。当前界面和 Agent 测试已区分执行/诊断以及 delivery、verification 等结果状态。因此总体设计把以下概念分开：

- 工具或命令是否执行；
- Agent 是否形成最终回答；
- 目标文件是否实际写入；
- 文档或结果是否完成可验证的交付；
- 是否因等待用户确认而暂停。

这种区分可防止 UI 在缺少证据时错误宣称“已完成”。

## 5. 分层职责详解

### 5.1 Core：领域模型与本地事实源

Core 负责：

- 项目与会话的领域表示；
- 用户设置及运行配置；
- 会话轮次和结构化条目的持久化；
- append-only 日志的追加与读取；
- 将本地历史转换为 Agent 可消费的数据。

append-only 是审计友好的存储原则：新增状态以记录方式写入，历史过程不被最终状态覆盖。它使执行轨迹成为产品的一等数据，也为中断恢复、问题定位和桌面重开后的历史展示提供基础。

Core 不负责决定模型输出，也不执行命令。它是领域数据与持久化边界，而不是 Agent 调度器。

### 5.2 Agent：执行引擎

Agent 层包含以下主要能力：

| 组成 | 职责 |
|---|---|
| `classify` | 识别任务类型及文档、分析、修复等意图 |
| `plan` | 组织任务步骤和执行策略 |
| `protocol` | 定义 Agent 与宿主/模型之间的结构化消息和工具协议 |
| `provider` | 对接 Anthropic、OpenAI、DeepSeek 或兼容端点 |
| `state` | 管理一轮执行中的阶段、状态和中间结果 |
| `dedup` | 对重复或冗余的工具/执行结果进行收敛 |
| `lib` | 汇总 Agent 循环、任务路由、工具执行和测试入口 |

Agent 的核心控制流是一个受预算和状态约束的循环：读取上下文与历史，形成计划或模型请求，解析结构化动作，执行工具，收集结果，再继续推理或结束本轮。没有可用 Provider 时，系统仍可保留本地扫描、规划和工具能力，并应明确说明未调用模型，而不是伪造模型结果。

Agent 负责工具语义和执行结果，但最终是否允许执行由宿主权限策略决定。

### 5.3 Shell：宿主侧一轮执行编排

Shell 位于 Core 与 Agent 之上，负责把领域历史、运行配置和 Agent 引擎组合成一轮可执行的 turn。其价值是让 CLI 与桌面端复用同一套核心语义，而不必各自实现任务循环。

CLI 的公开执行入口为 `run_turn`。桌面端并不直接复制该入口，而是在 `src-tauri/src/run.rs` 中增加长生命周期运行、异步等待、审批交互和取消能力。

### 5.4 Tauri Host：桌面能力适配层

Tauri Host 负责四类工作：

1. **IPC 命令**：把 GUI 请求转换成类型明确的 Rust 调用。
2. **本地资源**：管理项目目录、设置、凭据、Agent、Skill、MCP 配置及文件选择。
3. **运行生命周期**：注册活跃 Run、启动后台执行、取消运行、汇总完成状态。
4. **展示投影**：通过 `view.rs` 输出 `ProjectView`、`SessionView`、`TurnView`、`ItemView` 等前端 DTO。

使用独立 View DTO 的意义是避免 GUI 依赖内部枚举和存储结构。内部协议变化时，可以先在 Host 层完成兼容和投影，再独立演进前端。

### 5.5 React GUI：交互与展示层

GUI 不直接访问文件系统、进程或凭据，而是通过 Tauri IPC 请求能力。其主要交互分为：

- 项目与会话导航；
- Composer 中配置 Provider、模型、Agent、Skill 和权限；
- 运行中展示轨迹、进度和审批入口；
- Inspector 中查看回答、变更文件、工具与 LLM I/O；
- Trace、Archive、Settings、MCP 和 Agent/Skill 管理；
- 文件查看、搜索、diff 与 Markdown 渲染。

前端将 live 数据与 fixture 数据隔离，使同一组件体系既服务于真实应用，也服务于确定性视觉回归。

## 6. 一轮任务的端到端流程

```text
用户选择项目与会话
        │
        ▼
Composer 组装消息、Provider、模型、Agent、Skill、权限
        │ Tauri IPC
        ▼
Host 创建 StartArgs 与 Run，执行参数和项目边界检查
        │ 后台运行
        ▼
Shell 准备会话历史和项目上下文
        │
        ▼
Agent 分类 / 规划 / Provider 调用 / 本地工具循环
        │
        ├─ 读取、搜索、分析 ───────────────┐
        ├─ 命令或写文件 → 权限策略检查  │
        │                       ├─ ask → 等待审批
        │                       ├─ auto → 按风险判断
        │                       └─ full → 项目内自动执行
        └─ 产生结构化 Item ───────────────┘
        │
        ▼
Core 追加会话与轮次记录
        │
        ▼
Tauri View 投影 → api.ts → React 会话、轨迹、结果与变更文件
```

更具体地说：

1. 用户在项目上下文中提交消息，并在 Composer 选择执行配置。
2. GUI 通过 `api.ts` 调用 Tauri 命令。
3. `run.rs` 创建或登记 `StartArgs`，将工作区、会话、模型和权限等信息交给 Shell/Agent。
4. Agent 读取公开历史和任务上下文，识别任务类型并规划下一步。
5. 若配置了 Provider，则由 Provider 层发起 HTTP 请求；网络错误、未配置凭据等情况作为明确状态进入轨迹。
6. 搜索、读取、命令和写文件等动作按工具协议执行。
7. 需要审批的动作生成等待点；GUI 展示审批上下文，用户允许或拒绝后 Run 继续或终止相应步骤。
8. 过程条目和最终结果追加到会话历史，前端通过 View DTO 获取一致结构。
9. 若任务涉及文件，Changed Files 与 File/Diff Viewer 使用结构化文件结果展示实际变更。

## 7. 运行状态、并发与审批

桌面端将“启动一个 Agent turn”视为有生命周期的 Run，而不是一次阻塞函数调用。`src-tauri/src/run.rs` 中的关键抽象包括：

- `Runs`：登记活跃运行，支持判断是否存活和取消；
- `StartArgs`：描述一次桌面运行的输入参数；
- `Approvals`：维护审批票据及等待/恢复过程；
- `ApprovalTicket`：把待审批动作与具体运行关联；
- `wait_point`：执行线程到达审批点后等待用户决定；
- `resolve`：由 GUI 提交允许或拒绝结果；
- `remember_session_allow` / `clear_session`：管理会话级放行记忆。

典型状态可抽象为：

```text
created → running ───────────────→ completed
             │  ▲                    │
             │  └ approval granted   ├→ failed
             ▼                      └→ cancelled
        waiting_approval
             │
             ├─ rejected → completed/cancelled/failed
             └─ timed out → failed
```

具体 UI 状态可能比该图更细，但核心原则不变：审批是运行状态的一部分；取消是协作式终止；最终状态必须由执行结果和验证证据决定。

## 8. 权限与安全架构

### 8.1 权限档位

| 档位 | 预期行为 |
|---|---|
| `ask`（默认） | shell 命令与写文件逐次等待审批 |
| `auto` | 普通命令可自动执行，危险命令和写文件仍需审批 |
| `full` | 项目工作区内的操作可自动执行，不建议无边界使用 |

危险命令识别覆盖 `rm`、`sudo`、`git push`、管道下载执行等高风险类别。安全策略应同时考虑命令类型、作用路径和会话级授权，而不能只看动作名称。

### 8.2 凭据隔离

Provider 凭据与普通设置分开存储：

- `settings.log` 保存普通设置；
- `credentials.log` 保存 API Key，并使用 `0600` 权限；
- GUI 只接收掩码，不回传明文；
- Provider 配置和密钥生命周期分离，便于审计和撤销。

### 8.3 边界原则

- GUI 只能通过受控 IPC 请求本地能力；
- 文件与命令操作必须绑定用户选择的项目上下文；
- API Key、模型原始输入输出和本地运行数据不得写入普通项目文件；
- Agent 读取的旧历史或外部内容应按非可信输入处理；
- 权限档位属于授权策略，不等同于操作系统沙箱，不能用它替代进程隔离和资源限制。

## 9. 本地数据与持久化

macOS 默认数据目录为 `~/Library/Application Support/Kodo`：

```text
settings.log      普通设置
credentials.log   Provider 凭据，权限 0600
projects.log      项目列表
sessions/         会话及轮次日志
```

数据组织具有以下特点：

1. 本地文件是运行时事实源，不依赖单独数据库服务。
2. 日志采用追加式记录，适合保留 Agent 过程与审计历史。
3. 会话按项目组织，项目与会话之间具有明确归属关系。
4. GUI 展示模型由 Host 的 View 层派生，不直接读取内部日志格式。

随着数据量增加，后续需要重点保证日志版本迁移、并发追加一致性、损坏恢复和敏感字段脱敏，而不能只依赖“追加文件”的简单假设。

## 10. Provider 与可扩展能力

### 10.1 AI Provider

Agent 通过 Provider 抽象支持：

- Anthropic；
- OpenAI；
- DeepSeek；
- 用户配置的自定义兼容端点。

Provider 层负责协议差异、HTTP 请求和响应归一化；上层只依赖统一的 Agent 消息与工具协议。未配置密钥时，应用仍允许本地能力运行，并需要在最终结果中诚实暴露该限制。

### 10.2 Agent、Skill 与 MCP

仓库包含项目 Agent、内置/用户 Agent、Skill 和 MCP 相关的数据模型与 GUI 页面。这些配置决定“由谁执行、遵循哪些工作流、可使用哪些外部能力”，而 Agent/Shell 决定“如何执行”。

合理的扩展边界是：

```text
Agent 配置：角色、提示词、默认工具或工作方式
Skill 配置：可复用任务流程与说明
MCP 配置：外部服务/工具能力的声明与连接信息
Provider 配置：模型服务协议与凭据
Core/Shell/Agent：统一执行、安全和持久化机制
```

MCP 的连接生命周期、工具发现和失败隔离应保持为适配器能力，不能绕过 Agent 的预算、审批和轨迹记录机制。

## 11. 可观察性与审计

可观察性不是附属 UI，而是系统架构的一部分。结构化 Item 使一次执行至少能回答：

- Agent 做了什么判断；
- 搜索或读取了哪些位置；
- 执行了哪个命令；
- 哪个动作正在等待审批；
- Provider 是否成功调用；
- 哪些文件发生变化；
- 最终结果为何完成、失败、取消或等待确认。

Trace、Inspector、LLM I/O Viewer、Changed Files 和诊断信息都消费同一类结构化执行记录。这样 GUI 不是根据最终文本猜测运行状态，而是展示 Host 投影出的事实。

日志和 UI 同时应避免泄露凭据、完整敏感环境变量或未经脱敏的 Provider 内容。

## 12. 测试与评估体系

项目使用不同层级验证不同风险：

| 层级 | 工具/位置 | 重点 |
|---|---|---|
| Rust 单元/集成测试 | `crates/*/tests` 及 crate 内测试 | 协议、分类、状态、持久化和执行逻辑 |
| Agent benchmark | `crates/agent/tests/agent_benchmark.rs` | 工具使用、任务路由与行为基准 |
| Online benchmark | `crates/agent/tests/online_benchmark.rs` | 真实 Provider 条件下的回归观察 |
| Evals | `evals` | 可重复的 Agent 能力评估 |
| TypeScript/ESLint | `apps/desktop` | GUI 类型与静态质量 |
| Playwright | `apps/desktop/tests/visual` | 关键行为、交互、状态和视觉快照 |

建议后续把架构契约单独纳入测试：IPC DTO 兼容性、日志迁移、审批状态机、取消竞态、凭据脱敏、Provider 错误归一化，以及 live/fixture 行为一致性。

## 13. 关键设计取舍

### 13.1 本地优先而非服务化

本地文件与 Tauri 宿主降低部署复杂度，适合代码和凭据留在用户设备上的场景；代价是跨设备、协作、弹性扩展和集中治理能力较弱。

### 13.2 append-only 而非仅保存最终状态

保存完整过程更符合 Coding Agent 的审计和恢复需求；代价是存储、索引和历史投影逻辑会逐渐复杂。

### 13.3 GUI/Rust 强边界

WebView 不直接获得宿主能力可缩小攻击面并保持依赖清晰；代价是所有功能必须显式设计 IPC 与 DTO。

### 13.4 Agent 与 Core 解耦

Agent 可以脱离桌面存储独立测试和复用，宿主负责组合；代价是跨层运行状态需要通过协议和编排保持一致。

### 13.5 默认逐步审批

审批提高普通写操作和命令执行的安全性；代价是批量任务交互成本更高，需要在 `auto`/`full` 与风险识别精度之间持续平衡。

## 14. 当前架构的演进关注点

以下方向不是对现有产品重新定位，而是现有分层自然产生的演进点：

1. **固化跨层契约**：为 IPC、Provider 消息、工具协议和本地日志增加版本字段与兼容策略。
2. **拆分桌面编排**：`main.rs`、`view.rs` 与前端 `api.ts` 承担较多适配职责，可按领域拆成 project/session/settings/provider/run 等子模块。
3. **统一执行状态机**：把 running、approval、cancel、verification 和 delivery 的转换规则集中定义，减少 Host、Shell 和 GUI 各自解释状态。
4. **建立日志迁移层**：对 append-only 文件增加 schema version、索引、原子写入和损坏恢复。
5. **强化能力授权**：Agent、Skill、MCP 和工具调用共享同一权限与审计链路，默认不能绕过审批。
6. **持续做凭据脱敏**：Provider 输入输出、诊断、Trace 和崩溃信息都应经过统一脱敏。
7. **防止演示路径漂移**：持续比较 fixture 与真实 View DTO 的契约，避免视觉测试通过但桌面行为不一致。
8. **控制前端复杂度**：Composer、App、文件查看器等模块较大，可在不改变外部 API 的前提下按状态、命令和展示组件拆分。

## 15. 总结

Kodo 的总体架构可以概括为“本地持久化领域核心 + 可复用 Agent 引擎 + 多宿主编排 + Tauri 安全边界 + React 可观察工作台”。

其中：

- Core 保存项目和会话事实；
- Agent 决定任务如何推理和调用工具；
- Shell 组织一轮执行；
- Tauri Host 管理本地能力、运行和审批；
- React GUI 将同一份执行事实呈现为对话、轨迹、回答和变更文件。

该设计最重要的架构不变量是：**所有执行都必须经过统一运行与权限边界，所有可观察结果都必须来自结构化记录，任何完成声明都必须有实际执行或验证证据。**
